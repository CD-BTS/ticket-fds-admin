## 1. 기존 Credit 및 위험 정책 (변경 전 코드 기준)

### 1.1 Credit 산출식

`CreditCalculator`, `CreditPolicyConstants`

```
BaseCredit     = 100 × (A + 5) / (A + 2N + 1.5C + 10)        A 정상 관람, N 노쇼, C 미입금 자동 취소
AI 감점        = 40 × clamp(anomalyScore, 0, 1)               anomalyScore 가 null 이면 0
Rule 감점      = min(30, 카드 + IP + 분산)
DynamicPenalty = min(70, AI 감점 + Rule 감점)
Credit         = Math.round(clamp(BaseCredit − DynamicPenalty, 0, 100))
```

| 항목 | 값 |
|---|---|
| 초기 Credit | 50 (이력이 없을 때의 BaseCredit 과 같다. `user_credit.credit_score` 기본값) |
| 관람 이력 | 정상 관람 1회마다 분자·분모 +1, 노쇼 분모 +2, 미입금 자동 취소 분모 +1.5 |
| AI 감점 | 최대 40 |
| 카드 공유 | `user_card` 의 카드 해시별 고유 계정 수 최댓값. 2~3계정 5점, 4계정 이상 15점 |
| IP 집중도 | 요청의 `recentIpAttemptCount`(최근 10분 같은 IP 시도 수)가 5 이상이면 5점 |
| 분산 | 요청의 `intervalVariance` 가 null 이 아니고 1.0 미만이면 5점 |
| Rule 최대 / 전체 최대 | 30 / 70 |
| 등급 | 40 이상 NORMAL, 20~39 SUSPICIOUS, 19 이하 HIGH_RISK (`user_credit.tier` 에 저장) |
| 반올림 | `Math.round` (0.5 는 올림. 39.5 → 40) |

### 1.2 위험 정책

`PolicyDecisionService.evaluatePolicy`. 위에서부터 먼저 맞는 것을 적용한다.

| 순서 | 조건 | 조치 |
|---|---|---|
| 0 | 최신 RiskAssessment 가 없다 (anomalyScore null) | Credit 40 이상 ALLOW / 20~39 REQUIRE_CAPTCHA / 19 이하 DELAY. RESTRICT 는 없다 |
| 1 | Credit < 20 **그리고** score ≥ 0.85 | RESTRICT |
| 2 | Credit < 20 **또는** score ≥ 0.70 | DELAY |
| 3 | Credit < 40 **또는** score ≥ 0.40 | REQUIRE_CAPTCHA |
| 4 | 그 외 | ALLOW |

### 1.3 갱신 시점

| 시점 | 동작 |
|---|---|
| `POST /api/v1/users/{userId}/credit/evaluate` | 최신 RiskAssessment 와 규칙으로 감점을 새로 계산하고 `dynamic_penalty` 를 저장한다. 백엔드 안에서 자동으로 호출하는 코드는 없다 |
| 관람 이력 변경 (CHECK_IN, NO_SHOW, 늦은 취소) | 감점을 새로 계산하지 않고 저장된 `dynamic_penalty` 를 그대로 쓴다 |
| 정책 결정 (`decidePolicy`, context `QUEUE_JOIN` / `BOOKING_ATTEMPT`) | 그 시점의 저장된 Credit 과 최신 RiskAssessment 로 판정한다. Credit 을 다시 계산하지 않는다 |

### 1.4 null 과 데이터 부족

| 상황 | 현재 동작 |
|---|---|
| RiskAssessment 없음 | AI 감점 0. 정책은 0번 분기 (Credit 만으로 판정) |
| `intervalVariance` null | 분산 감점 제외 (이미 구현돼 있다) |
| `recentIpAttemptCount` null | 컨트롤러가 0 으로 바꾼다. IP 감점 제외 |
| `dynamic_penalty` null | 평가 이력이 없으면 0, 있으면 점수를 그대로 둔다 (#56) |

### 1.5 문서·전제와 실제 코드의 차이

| # | 전제 | 실제 코드 |
|---|---|---|
| 1 | 분산 감점이 `FeatureAggregationService` 의 `bookingIntervalVariance` 를 쓴다 | 요청 본문의 `intervalVariance` 를 쓴다. 두 값을 잇는 코드가 없다 |
| 2 | IP 감점이 `ipBookingDensity` 와 관련 있다 | 별개의 값이다 (최근 10분 같은 IP 시도 수). 호출자가 넘긴다 |
| 3 | 카드 감점이 `cardReuseCount` 를 쓴다 | `user_card` 테이블을 쓴다 (등록 카드 기준). Feature 는 예매 이벤트 기준이다 |
| 4 | AI 점수가 저장된다 | `/predict` 호출과 `RiskAssessment` 저장 코드가 없다. 테스트만 직접 저장한다 |
| 5 | 정책 문서 | `docs/ai-design.md` 는 빈 파일이다. 감점·정책 기준은 코드와 테스트에만 있다 |
| 6 | 등급 이름 | `tier` 의 기본값은 `BASE` 인데 평가 뒤에는 `NORMAL / SUSPICIOUS / HIGH_RISK` 가 들어간다 |
| 7 | Credit 계산의 사본 | `demo-ticketing/frontend/src/risk/credit.ts` 에 같은 계산이 따로 있다 (이번 범위 밖) |

## 2. 최종 AI 모델과의 불일치

최종 모델(ai 저장소 `REPORT_FINAL_MODEL.md` 6절, `predict_feature_spec.md` 4절)의 `anomalyScore` 는 **탐지 임계값을 0.5 에 맞춘 값**이다. 이전에는 학습 사용자 대비 백분위였다.

| # | 불일치 | 영향 (합성 데이터, 신규 사용자) |
|---|---|---|
| 1 | AI 감점 `40 × score` 는 탐지되지 않은 계정(score < 0.5)도 감점한다 | 정상 계정의 99.5% 가 감점을 받는다. 중앙값 6.7점 |
| 2 | 신규 사용자는 score 가 약 0.27 이상이면 Credit 이 40 미만이 된다 (감점 10.5 초과) | 정상 계정의 28.5% 가 SUSPICIOUS 가 되어 `Credit < 40` 조건으로 CAPTCHA 대상이 된다 |
| 3 | CAPTCHA 기준 0.40 이 탐지 기준 0.50 보다 낮다 | 정상 계정의 14.0% 가 0.40 이상이다 (0.50 이상은 5.6%) |
| 4 | 분산 감점: 백엔드의 v1 분산은 간격 1개부터 계산한다 (간격 1개면 0) | v1 값을 넘기면 정상 계정의 약 23% 가 분산 감점을 받는다 (5.6절. 참고 분석) |
| 5 | `risk_assessment.anomaly_score` 가 NOT NULL 이다 | `INSUFFICIENT_DATA` 를 "점수 없음" 으로 저장할 수 없다 |
| 6 | 정책·Credit 이 `model_version` 을 보지 않는다 | 이전 모델의 점수가 남아 있으면 새 기준으로 잘못 판정한다 |

**신규 사용자가 각 조치를 받기 시작하는 score** (규칙 감점별. `sim_score_boundaries_new_user.csv`, 0.01 단위)

| 규칙 감점 | A: CAPTCHA | A: DELAY | A: RESTRICT | D: CAPTCHA | D: DELAY | D: RESTRICT |
|---|---|---|---|---|---|---|
| 0 | 0.27 | 0.70 | 0.85 | 0.50 | 0.70 | **0.89** |
| 5 | 0.14 | 0.64 | 0.85 | 0.50 | 0.70 | 0.85 |
| 10 | 0.02 | 0.52 | 0.85 | 0.50 | 0.70 | 0.85 |
| 15 | 0.00 | 0.39 | 0.85 | 0.00 | 0.70 | 0.85 |

- 기존 정책(A)에서 CAPTCHA 는 사실상 0.40 이 아니라 0.27 에서 시작한다. 규칙 감점이 있으면 더 낮다.
- A 에서는 규칙 감점이 있는 계정이 score 0.39~0.70 에서도 Credit 조건으로 DELAY 를 받는다. D 에서는 score 0.70 이 기준이 된다.
- D 에서 규칙 감점이 없는 신규 사용자는 score 0.89 부터 RESTRICT 다 (A 는 0.85).

## 3. 수정 후보와 근거

| 후보 | 내용 | 근거 |
|---|---|---|
| 4-1 AI 감점 | `40 × score` → `40 × max(0, 2 × score − 1)` | score 0.5 미만은 모델이 "탐지하지 않음" 으로 본 계정이다. 0.5 에서 0, 1.0 에서 40 으로 차등 감점과 최대 40점을 유지한다 |
| 4-2 분산 감점 | 유효 간격 5개 이상일 때만 분산을 계산하고, null 이면 감점 제외. 임계값 1.0 과 5점은 유지 | Feature 정의 v2 와 같다. 시도가 2~5건인 계정의 분산은 0 이거나 매우 작아 규칙이 잘못 걸린다 |
| 4-3 CAPTCHA 기준 | score 0.40 → 0.50 | 모델의 탐지 기준과 맞춘다. DELAY 0.70, RESTRICT 0.85 + Credit < 20 은 그대로 |

비교한 조건

| 조건 | AI 감점식 | CAPTCHA 기준 |
|---|---|---|
| A 기존 | `40 × s` | 0.40 |
| B | `40 × max(0, 2s − 1)` | 0.40 |
| C | `40 × s` | 0.50 |
| D | `40 × max(0, 2s − 1)` | 0.50 |

분산 감점은 네 조건 모두 v2 정의(간격 5개 미만이면 null → 감점 없음)로 계산했다. v1 과의 차이는 5.6절에 따로 적었다.

| 모델과의 일관성 | 탐지되지 않은 계정(score < 0.5)은 AI 감점도, score 기준 CAPTCHA 도 받지 않는다 |
| 규칙 감점에 대한 여유 | 기존 감점식은 규칙 감점 5점만 더해져도 정상 계정 제재가 57.7% 가 된다 (가정 조건). D 는 5.6% 그대로다 |
| 4-1 과 4-3 을 함께 | C 만으로는 신규 사용자에게 효과가 없다 (A 와 같다). B 만으로는 이력이 있는 사용자와 score 0.40~0.50 구간이 남는다 (정상 8.4%p, 매크로 5.6%p) |
| 최소 수정 | 코드 두 줄. 새 규칙이나 새 임계값이 없다 |

### 7.2 알고 받아들인 비용

1. **매크로의 DELAY 적용률이 줄어든다: 34.2% → 23.6%.** 선점·취소 33.0% → 16.8%, 고정 간격 31.1% → 18.2%, 랜덤 지연 30.2% → 18.4%, 다중 계정 40.7% → 38.8%. 줄어든 10.6%p 는 CAPTCHA 로 내려간다. 이들은 score 가 0.70 미만이고 기존에는 AI 감점과 규칙 감점이 합쳐져 Credit 20 미만이 되던 계정이다. 이 감소는 정상 사용자 보호와 맞바꾼 것이 아니라 감점식 변경에 따라오는 부작용이다 (같은 이동이 정상 계정에서는 3건).
2. **매크로의 ALLOW 가 8.0% → 19.9% 가 된다.** 모두 모델이 탐지하지 못한 계정이다. 단독으로 움직이는 고정 간격·랜덤 지연 매크로는 약 40% 가 ALLOW 다.
3. **RESTRICT 가 유지되는 것(16.8%)은 특정 시뮬레이션 조건에 한정된다.** "신규 사용자 + 카드 감점을 `card_reuse_count` 로 대신함" 조건의 결과다.
   - 카드 감점이 없으면 16.8% → 11.5% (다중 계정 57.9% → 39.6%). 기존 정책은 이 조건에서도 16.8% 다.
   - 정상 관람 5회 이력이 있으면 16.2% → 9.2%, 10회면 4.0% → 2.1%.
   - 규칙 감점이 없는 신규 사용자는 score 0.89 부터 RESTRICT 다 (기존 0.85).
   - 실제 `user_card` 가 대용 변수만큼 카드 공유를 잡지 못하면 RESTRICT 는 줄어든다.

### 7.3 선정에 쓴 가정

| 가정 | 선정에 미치는 영향 |
|---|---|
| IP 집중도 감점을 재현하지 못해 0 으로 뒀다. `ipBookingDensity` 로 대체하지 않았다 | 공유 IP 사용자의 결과가 낙관적일 수 있다. "모든 계정에 5점" 조건(실제 감점 여부가 아닌 가정)에서도 A 와 D 의 순서는 같다 |
| 카드 감점은 `card_reuse_count` 대용 변수다 (실제는 `user_card`) | 정상 계정 결과에는 영향이 없다. D 의 RESTRICT 유지가 이 값에 의존한다 (7.2 의 3) |
| 합성 정상 계정에는 카드 공유와 낮은 분산이 거의 없다 | 정상 사용자가 규칙 감점을 받는 경우를 평가하지 못했다 |
| 모든 계정이 신규 사용자 (BaseCredit 50) | 이력 조건 비교는 모든 계정에 같은 이력을 준 것이다 |

### 7.4 채택하지 않은 것

- **B**: 매크로 CAPTCHA 가 더 넓다 (매크로 ALLOW 14.3%, 정상 CAPTCHA 13.4%). 0.40~0.50 구간에서 CAPTCHA 를 받는 계정이 이 데이터에서 정상 2,030 대 매크로 333 이고, DELAY 감소는 B 에서도 똑같이 생긴다.
- **C**: 신규 사용자에게 효과가 없다.
- **DELAY 기준 조정**: DELAY 감소를 되돌리려면 DELAY 기준을 다시 봐야 한다. 이번 이슈는 DELAY·RESTRICT 기준 유지가 전제라 다루지 않았다. 필요하면 별도 이슈로 다룬다.

## 10. 검증의 한계

- **합성 데이터다.** 실제 사용자에 대한 제재율·오탐률은 알 수 없다. D1·D2·D3 는 정상 사용자 속도에 대한 가정이고 어느 것도 실제 분포가 아니다.
- **독립 검증이 아니다.** #20 의 독립 검증 데이터를 정책을 비교하고 고르는 데 썼다. 채택한 정책의 성능을 따로 검증한 것이 아니다. 다만 후보 넷은 데이터를 보기 전에 정해져 있었고, 임계값을 이 데이터로 맞추지 않았다.
- **IP 집중도 감점을 재현하지 못했다.** 최근 10분 같은 IP 시도 수가 저장된 Feature 표에 없다. 기본 결과는 IP 감점 0 이다. 공유 IP 사용자는 실제로 이 감점을 받을 가능성이 높아, 5.2절의 공유 IP 결과는 낙관적일 수 있다 (전원 5점 조건에서 D 의 공유 IP 등급 하락은 5.2% → 9.2%, 조치는 거의 같다).
- **카드 감점은 대용 변수다.** `card_reuse_count` 는 예매 이벤트 기준이고 실제 규칙은 `user_card`(등록 카드) 기준이다. D 의 RESTRICT 유지가 이 값에 의존한다 (5.4절).
- **합성 정상 계정에는 카드 공유와 낮은 분산이 거의 없다.** 정상 사용자가 규칙 감점을 받는 경우(가족 카드 등)의 영향은 평가하지 못했다.
- **모든 계정이 신규 사용자라고 가정했다.** 실제 Credit 은 관람 이력에 따라 다르다. 이력 조건은 모든 계정에 같은 이력을 준 것이며 정상 사용자와 매크로의 이력 차이를 반영하지 않는다.
- **평가가 한 번만 일어난다고 봤다.** 실제로는 평가 시점과 정책 결정 시점이 다르고, 평가가 오래된 경우가 있다.
- **시도가 없는 계정이 데이터에 없다.** `INSUFFICIENT_DATA` 와 호출 실패는 코드 경로 검토로만 다뤘다.
- 분산 v1 / v2 비교(5.6절)는 모델 선정에 쓴 데이터에서 했고, 모델에 v1 분산을 입력했을 때의 점수 변화는 보지 않았다.
- CAPTCHA·DELAY 가 실제 매크로를 얼마나 막는지는 이 시뮬레이션의 대상이 아니다. 적용률만 비교했다.
- 모델을 다시 학습하면 점수의 눈금이 바뀐다 (#20 12절). 0.50 은 정의상 유지되지만 0.70, 0.85 에 해당하는 비율은 달라진다.
